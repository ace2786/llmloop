# v3 改进预期（查询改写）

> 说明：代码已改完，**本文件写在跑 v3 之前**（2026-10-27 17:33）
> 基线：v1 = 参数名加权 + top-k 6

---

## 一、为什么做 v3

**v1 的遗留问题**：测试集从 77% 降到 71%，说明改动没有泛化。

**诊断出的具体原因**（见 `out/report.md` 第四节）：
- 参数名加权能救「难题」（8% → 65%）
- 但会伤「易题」（100% → 93%）

**v3 换个思路：不改检索打分，改「查询本身」。**

---

## 二、改什么

```
在检索之前，用 GLM 把用户问题改写成「含参数名 + 同义词」的形式

例：
原问题：为什么 DPO 训练时 ref_model 不指定为初始的 SFT 完的模型？
改写后：DPO 训练 ref_model 参考模型 为什么不用初始 SFT 监督微调模型初始化...

原问题：temperature 等参数怎么设？
改写后：如何设置 temperature top_p top_k 推理参数
```

**关键设计：**
- 改写只用于检索，**回答时仍用原问题**（避免改写跑偏影响回答）
- 改写失败时回退到原问题（不影响主流程）
- 保留 v1 的参数名加权 + top-k 6（叠加，不是替换）

**所以 v3 vs v1 的差异 = 查询改写的净贡献。**

## 三、预期（★ 先写死）

| 指标 | v0 | v1 | **v3 预期** |
|---|---|---|---|
| 优化集正确率 | 56% | 80% | **85%+** |
| 测试集正确率 | 77% | 71% | **78%+（超过 v0）** |
| 检索没命中（优化集） | 22 条 | 8 条 | **5 条以下** |

**核心假设**：v1 在测试集上掉分，是因为「泛问法检不到」；
查询改写能补出隐含术语，所以测试集应该回升。

---

## 四、风险

| 风险 | 表现 | 应对 |
|---|---|---|
| **改写跑偏** | 检到完全无关的段落 | 对比 v1/v3 的检索结果，看是否变差 |
| **改写过长** | BM25 被无关词稀释 | 限制输出长度（代码里已限 300 字） |
| **改写成本** | 每题多一次 LLM 调用 | 60 题约 3-5 分钟，可接受 |
| **改写不稳定** | 同一题两次改写不同 | 无法控制，属于 LLM 固有随机性 |

## 五、验证方法

1. 跑 `week1.py --split optimize --version v3 --rewrite --topk 6`
2. 跑 `week1.py --split test --version v3 --rewrite --topk 6`
3. 生成盲判表，人工判 120 条
4. 对比 v0 / v1 / v3（优化集 + 测试集）
5. **重点看**：v1 在测试集上错、v3 对的题（查询改写救回了什么）

## 六、诚实声明

- 查询改写用 LLM 做，存在随机性，同一题多次运行结果可能不同
- 本次只跑一轮，未做多次采样平均
- 若测试集仍未回升，说明「泛问法」不是唯一原因
